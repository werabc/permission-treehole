## 二、已修复的问题

### 🔴 CRITICAL 级修复

#### C-1: JWT 密钥外部化
- **文件**：`JwtTokenProvider.java`
- **变更**：构造器改为 `@Value("${jwt.secret:}")` 注入 → 环境变量 `JWT_SECRET_KEY` → dev 兜底（带警告日志）
- **新增**：密钥长度 ≥ 32 字节（256 bit）校验，不满足抛 `IllegalArgumentException`
- **效果**：生产/测试环境通过环境变量注入密钥，源码中无有效密钥残留
- **部署要求**：生产服务器设置 `JWT_SECRET_KEY` 环境变量（Base64 编码、≥ 32 字节）

#### C-2 / H-2: validateToken 不再抛异常
- **文件**：`JwtTokenProvider.java`、`JwtAuthenticationFilter.java`
- **变更**：
  - `validateToken()` 将 `ExpiredJwtException` 改为返回 false（而非重抛）
  - `JwtAuthenticationFilter` 删除 `ExpiredJwtException` 独立 catch 块
  - Filter 中的泛型 `Exception` catch 现在返回 401（fail-closed），不再继续放行
- **效果**：认证子系统任何异常都返回 401，消除 fail-open 风险

### 🟠 HIGH 级修复

#### H-1: 权限查询遗漏软删除过滤
- **文件**：`SysUserMapper.java` → `selectPermissionsByUserId`
- **变更**：新增 `INNER JOIN sys_role r ON r.id = ur.role_id` + `AND r.status = 1 AND r.deleted = 0`
- **效果**：软删除的角色不再授权任何权限

#### H-2: 密码 hash 不回显
- **文件**：`SysUserServiceImpl.java` → `pageUsers()`、`getUserById()`
- **变更**：返回前执行 `user.setPassword(null)`
- **效果**：API 响应中不再包含 BCrypt 哈希

#### H-3: 操作日志密码脱敏
- **文件**：`OperationLogAspect.java`
- **变化**：
  - 正则替换：`password`、`oldPassword`、`newPassword`、`confirmPassword`、`captchaCode` → `***`
  - 请求参数截断至 4000 字符（防 DB 溢出）
  - `insert()` 操作外层 try-catch，**日志写入失败不阻塞业务请求**
- **效果**：日志中不存明文密码

#### H-4: 黑名单 TTL 精度修复
- **文件**：`SysUserServiceImpl.java` → `logout()`
- **变更**：
  - TTL 单位从 `MILLISECONDS` 改为 `SECONDS`
  - 仅当 `remaining > 1000ms` 才写入黑名单
  - `Math.max(remaining / 1000, 1)` 保证最小 1 秒
- **效果**：消除近过期 token 黑名单写入失败的问题

#### H-5: 角色详情接口去错字段
- **文件**：`SysRoleServiceImpl.java` → `getRoleById()`
- **变更**：移除 `role.setDeptIds(menuIds...)`（menu IDs 不应写入 deptIds）
- **效果**：前端 `/{id}/menus` 单独调用获取菜单 ID，不再混淆

### 🟡 MEDIUM 级修复

#### M-1: null-safe 角色状态检查
- **文件**：`UserDetailsServiceImpl.java` → `buildLoginUser()`
- **变更**：`role.getStatus() != null && role.getStatus() == 1`
- **效果**：防止数据库脏数据（status=null）触发 NPE

#### M-2: dataScope 只读一次角色表
- **文件**：`UserDetailsServiceImpl.java`
- **变更**：角色列表只查一次，权限和 dataScope 共用同一份 roleList
- **效果**：消除重复的 `selectBatchIds(roleIds)` 调用

#### M-3: 数据初始化不打印密码
- **文件**：`DataInitializer.java`
- **变更**：启动日志改为 "默认账号: admin, tech, backend (密码见 application.yml 或通过环境变量配置)"
- **效果**：日志聚合系统不再含明文默认密码

#### M-4: 登出接口 header 防御
- **文件**：`AuthController.java` → `logout()`
- **变更**：`@RequestHeader(value = ..., required = false)` + `StrUtil.isNotBlank` 守卫
- **效果**：Authorization 头缺失时返回 200（幂等），不再 NPE

#### M-5: LIKE 通配符转义
- **文件**：`SysMenuServiceImpl.java`、`SysDeptServiceImpl.java`、`SysUserServiceImpl.java`（pageUsers）
- **变更**：查询 keyword 调用 `.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_")`
- **效果**：用户输入的 `%` / `_` 不再被解析为 LIKE 通配符

#### M-6: 业务异常支持 cause 链
- **文件**：`BusinessException.java`
- **变更**：新增 `BusinessException(ResultCode, String, Throwable)` 和 `BusinessException(int, String, Throwable)`
- **效果**：异常链不丢失，便于根因排查

## 三、未修复（需架构调整，建议后续迭代）

| 问题 | 原因 | 建议 |
|------|------|------|
| Refresh Token 无旋转（Rotation） | 需服务端持久化 Token 状态，当前架构无 Refresh Token 存储 | 引入 Redis Token Family + JTI，或使用 Spring Authorization Server |
| 退出登录不失效 Refresh Token | Logout 接口只接收 Access Token，无法获取对应 Refresh Token | 请求体同时传 refresh_token，或存储 access↔refresh 绑定关系 |
| getClientIp 在多层代理/伪造场景受限 | 需配合 Spring ForwardedHeaderFilter + trusted proxy 配置 | 部署层统一配置 `server.forward-headers-strategy=native` |
| deptIds 列表在 `CUSTOM` 数据范围下为空 | 当前未实现自定义部门范围的前端配置入口 | 新增角色-部门关联表或字段后补充 LoginUser.buildLoginUser 逻辑 |

## 七、后续优化建议

1. **引入 Refresh Token 旋转**：每次 refresh 后旧 RT 失效，新 RT 签发，配合 JTI 存储在 Redis 实现复用检测
2. **操作日志异步化**：将 `OperationLogAspect` 中的同步 insert 改为 `@Async` 线程池或 MQ 异步落库
3. **数据范围 SQL 拦截器**：实现 MyBatis-Plus 的 `InnerInterceptor`，根据 `LoginUser.dataScope` 自动拼接部门过滤条件
4. **配置化验证码开关**：`captcha.enabled=true/false`，关闭后 login 不校验验证码
5. **Swagger Profile 隔离**：生产 profile 下禁用 `/doc.html` 与 `/v3/api-docs/**`
