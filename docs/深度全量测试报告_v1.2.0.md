## 三、缺陷发现与修复（本轮共 7 个）

### 🔴 P0-1 点赞功能 100% 失败（历史遗留）

`th_like` 表缺 `update_time` 列，而 `ThLike` 实体继承 `BaseEntity`，MyBatis-Plus 的 INSERT 会带上该列：

```
java.sql.SQLSyntaxErrorException: Unknown column 'update_time' in 'field list'
```

**这意味着"点赞"这个核心功能从项目建立以来就没成功过一次。**
修复：`create_tables.sql` 与 `migration_v1.2.0.sql` 补列（保持与实体一致）。

### 🔴 P0-2 举报闭环是"死代码"

上一轮我在 `ThReportServiceImpl.handleReport` 里实现了完整闭环（下架内容 / 违规计分 / 自动处罚 / 通知举报人），
但 `ThReportAdminController.handle` **自己又写了一遍"只改状态"的旧逻辑**（还绕过 Service 直接 `updateById`），
导致管理端处理举报时闭环完全没跑。

修复：控制器与批量处理接口统一委托给 `ThReportService.handleReport`。
验证：现在处理举报后 —— 内容自动下架 ✓、作者违规 +2 分 ✓、举报人收到 `REPORT_RESULT` 通知 ✓。

### 🟠 P1-3 数据权限把部门树"打散"

数据范围过滤按 `id IN (可见部门)` 施加到 `sys_dept`，父节点被过滤掉后前端建树找不到父节点，**整棵组织树渲染为空**。
修复：新增 `deptTreeIds = 可见部门 + 全部祖先`，仅用于 `sys_dept` 查询；
`sys_user` 仍用精确集合，**避免补祖先导致可见用户范围被放大（越权）**。已补单测锁定该边界。

### 🟠 P1-4 改密后旧 Token 依然可用（安全问题）

`JwtAuthenticationFilter` 只校验黑名单，而改密逻辑仅仅是删了 Redis 里的 token 缓存 → **旧 Token 继续有效**。
修复：改密时把该用户所有已签发 Token 拉黑（复用登出机制）。
过程中还踩到一个坑：缓存值可能是 `Long`（树洞端）或 `LoginUser` 对象（管理端），反序列化会抛
`Unrecognized field "enabled"`，因此改为**从 key 里的 JWT 解析 userId**，不再读缓存值。

### 🟠 P1-5 越权读：`GET /api/user/{id}/roles`
任意登录用户可查他人角色分配。修复：补 `@PreAuthorize("hasAnyAuthority('system:user:query','admin')")`。

### 🟠 P1-6 `/api/auth/**` 整段放行
收敛为精确白名单（`captcha` / `login` / `refresh` 放行，其余需认证），验证 `user-info`、`logout` 未带 Token 均返回 401。

### 🟡 P2-7 单测基线是坏的
`SysUserServiceImplTest` 4 个用例长期失败（继承的 `baseMapper` 无法被 Mockito 注入）。已用
`ReflectionTestUtils.setField` 修复，现在 61 个单测全绿。

## 五、已知限制与后续建议（诚实说明）

1. **写操作的越权防护**：MyBatis-Plus 的 `DataPermissionInterceptor` 只改写 SELECT。
   当前用户的 **UPDATE/DELETE 越权**靠权限码（`system:user:edit`）兜底，尚未按数据范围逐条校验。
   建议：在 `SysUserServiceImpl.updateUser/deleteUser` 等写路径补 `checkDataScope(targetId)`。
2. **Token 吊销用 `keys()` 扫描**：Redis 数据量大时有性能隐患。
   建议：维护 `user:{id}:tokens` 集合，吊销时按集合遍历。
3. **前端未做浏览器级 E2E**：本轮验证了后端接口全链路 + 两个前端 `npm run build` 通过，
   未启用真实浏览器点击流（需要额外搭建 Playwright/Cypress）。
4. **测试库可复现**：`scripts/e2e_test.sh` + `sql/e2e_seed.sql` 已入库，随时可一键复跑。
